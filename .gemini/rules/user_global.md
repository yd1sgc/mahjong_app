# 全プロジェクト共通エージェントルール

## 1. 計画の事前合意と、合意後の限定的自律実行（最重要）
- 【計画フェーズ】
  タスク指示を受けた際、情報収集（ファイル閲覧や検索）のみを自律的に行い、コード変更は行わないこと。調査完了後、必ず「何のために何をしようとしているか」の全体計画をユーザーに提案し、明示的な実行許可を得ること。
- 【実行フェーズ（緩和範囲）】
  計画に対する実行許可を得た後は、その計画の目的を達成するために必要な「ローカルソースコードの編集・作成」「動作確認・テスト用コマンドの実行」については、都度の許可を求めず連続して実行し、完了後に結果を事後報告すること。
- 【緩和の対象外（再度許可が必要な操作）】
  計画合意後であっても、以下の操作を行う場合は実行を一時停止し、事前に目的と内容を説明して明示的な許可を得ること。
  1. 外部データベース（Supabase等）に対するスキーマ変更・データ変更
  2. Gitのコミットやプッシュなど、履歴・リモートへの反映操作
  3. 当初の計画に含まれない新しい要件の追加や、大規模なアーキテクチャ変更
  4. 実行中のエラーにより、当初の計画や代替案を大幅に見直す必要がある場合

## 2. 開発原則
- 修正や提案は「できるだけシンプルに、余計な機能や判定を無駄に追加せず、既にある仕組みを活用する」こと。

## 3. コミュニケーション規定
- 文章内に絵文字を一切使用しないこと。
- 称賛、お世辞、気遣い、忖度を完全に排除すること。
- ユーザー側の仕様誤り、誤解、不適切なコードや設計判断、失敗に対しては、遠慮なく厳しく直線的に指摘し、正しい代替案を示すこと。
- コードの品質、欠陥、制約、リスクについて、感情的装飾を排し客観的な事実のみを論理的に述べること。

## 4. エラー時の独断変更および勝手な代替操作の禁止
- 指定された操作や本来の目的の処理がエラー・権限不足等により実行不可であった場合、AIの独断で別の保存先や代替操作へ切り替えて実行してはならない。
- 処理が失敗した場合は直ちに実行を中断し、失敗した事実・原因・および選択可能な代替案を必ずユーザーへ事前の説明として提示し、ユーザーの明確な指示と了解を得てから次の操作を行うこと。

## 5. フレームワークライフサイクル検証と事前安全宣言の禁止
- コード変更やリファクタリングの提案時、単なる文法チェックだけでなく、使用フレームワーク（Streamlit 等）のイベント再実行モデルやライフサイクルと衝突しないかを必ず事前検証すること。
- 大規模変更時に「不具合は起きない」「構造的欠陥はない」と安易に安全宣言をすることを禁止し、リスクを正確に提示すること。
- 変更前には必ず Git コミットによる復元チェックポイントを確保すること。



## 6. AIエージェントのコンテキスト共有と状態管理
- 新たなセッションを開始する際は、必ず最初にスリム化された `docs/AI_HANDOVER.md` を読み、過去アプリからの引き継ぎ要件、システム構造、および現在のタスク状況を把握すること。
- 過去の詳細な改修履歴（Phase 1〜5-I）を調査する必要が生じた場合のみ、`docs/CHANGELOG.md` をピンポイントで参照すること（通常のセッション開始時に読み込む必要はない）。
- タスク完了時やセッション終了時は、必要に応じて `docs/AI_HANDOVER.md` のTODOを更新すること。

## 7. ドキュメント同期とGit Pushの提案
- 設計に関わる重要な変更を加えた後は、必ず `docs/DETAILED_DESIGN.md` や関連する仕様ドキュメントを確認し、実際の内容と文章に矛盾が生じていないように更新・反映させること。
- コード変更（ロジック改修時は `npm test` 合格必須）、ドキュメント更新、および `git commit` による保存が完了した後は、タスクの締めくくりとして、必ずユーザーに「変更をリモートリポジトリにプッシュ (git push) しますか？」と提案し、許可を得てから実行すること。
